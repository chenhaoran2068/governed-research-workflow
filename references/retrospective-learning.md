# Retrospective Learning

## Purpose And Boundary

Use a retrospective to retain an evidence-backed lesson about how work was
organized, checked, repaired, or handed off. It is not a scientific audit, a
readiness decision, a compliance certification, or a judgment about whether a
study succeeded.

Do not use retrospective work to validate results, approve a protocol, decide
that a manuscript is ready, or assign blame to a person or agent. Route a
scientific, compliance, data, or submission concern to the appropriate
specialized process instead.

## Choose A Bounded Mode

Use the smallest mode that preserves the lesson.

| Mode | Appropriate trigger | Intended output |
| --- | --- | --- |
| Milestone snapshot | A useful process pattern or repair is clear while work continues. | Short project-local observation and next trigger. |
| Pre-submission reflection | Internal release or submission preparation is approaching. | Cross-cutting process lessons and unresolved workflow risks, without release approval. |
| Post-submission or revision reflection | A technical return, reviewer cycle, transfer, or revision exposes a lesson. | Route-specific observations and possible improvements. |
| Closeout reflection | The project reaches a stable archive or stop point. | Archive-ready process summary and promotion decisions. |
| Incident or near miss | A defect, rollback, ambiguity, or recovery could recur. | Narrow preventive lesson with an action and limitation. |

Do not require a retrospective after ordinary edits. An invitation to reflect
at a milestone is not a claim that the project is complete or ready to submit.

## Label What Is Known

Keep these categories distinct:

| Label | Meaning |
| --- | --- |
| Recorded project fact | Directly supported by a project record or approved artifact. |
| Observed pattern | A supported pattern across one or more events. |
| Working explanation | A plausible but unconfirmed account of why an event occurred. |
| Candidate lesson | A proposed future behavior with a stated scope and limitation. |
| Accepted reusable rule | A user-approved lesson already integrated into a live artifact. |
| Local note | Context that should not be generalized. |

Do not present an explanation, missing record, or remembered conversation as a
proven project fact.

## Minimal Retrospective Loop

1. Declare the mode, narrow process surface, non-audit boundary, and available
   evidence before reviewing records.
2. Retain only the minimum non-sensitive pointers needed to support each
   observation. Do not copy source text, private prompts, patient data,
   credentials, unpublished content, or confidential correspondence.
3. Decide whether the observation should remain project-local or is a candidate
   for broader use. Existing live guidance should be linked, not duplicated.
4. For a reusable candidate, state its trigger, recommended behavior, benefit,
   scope, exclusions, and proposed destination.
5. Obtain an explicit human decision: accept, revise, defer, reject, or keep
   local only. Do not promote a lesson automatically.
6. When promotion is accepted, update the selected live rule, template,
   checklist, workflow, or skill and verify that the new route is usable.

## Promotion Test

A lesson may be considered for broader use only when it is likely to recur,
changes a default check or workflow boundary, has an actionable future
behavior, and is not already adequately covered by existing guidance.

Keep it local when it depends on a particular dataset, institution, disease,
journal, user preference, or unresolved causal explanation.

## Required Human Controls

Stop and seek human direction when the retrospective would expose restricted
material, become a disguised study-quality assessment, imply submission
readiness, or alter shared/public guidance. A project observation does not
become public or reusable merely because it is well written.
